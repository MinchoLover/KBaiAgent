# KB AI Challenge 기술설명서

## KBaiAgent: 계약서 한 장을 검증 가능한 금융 의사결정으로

> **AI는 읽고, 코드는 계산하고, 사람은 확인하고, KB는 결정한다.**

### 한 줄 소개

KBaiAgent는 수출입 계약서·인보이스의 비정형 정보를 AI로 구조화하고, 원문 근거와
사용자 확인을 통과한 값만 결정론적 금융 엔진에 전달하여 환노출·현금흐름·운영자금
위험을 계산한 뒤, 기업과 KB 담당자가 바로 상담을 시작할 수 있는 근거 중심의
상담 패킷으로 변환하는 수출입 금융 의사결정 지원 에이전트다.

---

## 1. 개발 배경과 해결하려는 문제

환율 전망은 “시장이 어디로 움직일 것인가”를 설명하지만, 수출입 기업의 자금
담당자가 실제로 답해야 하는 질문은 다르다.

- 보유 외화와 기존 헤지를 제외하면 이번 계약에서 실제로 열려 있는 환노출은 얼마인가?
- 환율이 불리하게 움직일 때 원화 지급액 또는 수취액은 얼마나 달라지는가?
- 결제 또는 수취 이후에도 최소 운영자금을 유지할 수 있는가?
- 현금과 대출한도를 반영한 뒤에도 실제 지급 부족이 남는가?
- 환율, 대금 회수, 운영자금 중 무엇을 먼저 은행과 상담해야 하는가?

기존 업무에서는 계약서 확인, 환율 정보, 엑셀 계산, 금융상품 검색과 은행 상담 준비가
서로 분리되어 있다. 이 때문에 동일 정보를 반복 입력하고, 결제일이나 통화를 잘못
옮기며, “운영자금 목표 미달”을 “지급불능”으로 과장하는 등 금융 의미가 왜곡될 수
있다. 범용 LLM에 문서를 그대로 넣어 계산과 추천까지 맡기면 자연어 처리의 편리함은
얻지만 숫자의 재현성, 원문 추적성, 최신 상품 근거와 책임 경계를 잃기 쉽다.

KBaiAgent의 기술 목표는 단순한 환율 계산기나 상품 추천 챗봇을 만드는 것이 아니다.
**비정형 문서에서 확인된 거래 사실을 만들고, 그 사실을 기업별 현금 영향으로
변환하며, 모든 숫자의 근거를 보존한 채 사람의 금융 상담으로 연결하는 것**이 핵심이다.

## 2. 제안 솔루션

KBaiAgent는 다음의 `Contract-to-Decision` 파이프라인을 제공한다.

```text
PDF·PNG·JPEG 무역문서
        ↓
AI 구조화 추출 + Pydantic 스키마
        ↓
원문 evidence 대조 + 정규화 + 사용자 확인
        ↓
팀 Stage 1 시장모델(JSON/REST) + 독립 기준환율
        ↓
Decimal 환노출·시나리오·날짜별 현금흐름 계산
        ↓
제약 기반 대응 후보 + 거래·국가 맥락 + 공식자료 후보
        ↓
위험 기반 상담 Top 3 + ConsultationPacket JSON
        ↓
Streamlit 화면 · Markdown handoff · 검증된 설명 보고서
```

사용자는 네 개의 업무 화면만 따라가면 된다.

1. **거래 분석**: 거래 당사자, 거래 방향, 통화, 금액, 결제일을 원문과 대조한다.
2. **환율 전망·위험**: 환율 방향·중심값·범위와 horizon을 확인하고, 검증된 고정
   스트레스가 원화 현금과 운영자금 버퍼에 미치는 영향을 본다.
3. **금융지원 추천**: 필요한 거래조건을 명시적으로 확인하고 한 번의 저장 동작으로
   공식 금융지원 Top 3와 별도 보조 서비스를 갱신한다.
4. **상담 준비·보고서**: 상담 순서, 최신 금융후보, 준비서류와 기관 질문을 확인하고
   같은 패킷에서 생성된 상담 준비서를 내려받는다.

## 3. 전체 시스템 아키텍처

| 계층 | 역할 | 핵심 구현 |
|---|---|---|
| Stage 0 | 문서 구조화, evidence 검증, 사용자 확인 | `src/document_intake/`, `validators.py` |
| Stage 1 | 팀 시장모델 연동, 기준환율 결합, horizon 판정 | `src/stage1/`, `src/application/market_integration_service.py` |
| Stage 2 | 환노출, 환율 시나리오, 날짜별 현금흐름 | `src/stage2/` |
| Stage 3 | 명시적 제약을 만족하는 대응 후보 탐색 | `src/stage3/` |
| Stage 4 | 공식 출처 기반 자료 검색·후보 제한 | `src/stage4/` |
| 상담 계층 | 위험 분류, 핵심 검토 분야·추가 확인사항, canonical handoff | `src/consultation/` |
| Stage 5 | 계산 결과 설명, critic, 결정론 fallback | `src/stage5/` |
| Workflow/UI | 상태·gate·fallback·trace, 사용자 화면 | `src/workflow/`, `app.py`, `src/ui/` |

팀의 Stage 1 환율모델은 메인 애플리케이션 안에 복제하지 않고 별도 프로세스로
유지한다. KBaiAgent는 합의된 JSON/REST adapter 계약으로만 결과를 소비한다. 따라서
시장모델과 기업금융 의사결정 계층을 독립적으로 개선할 수 있고, provider 장애 시에도
고정 스트레스 기반의 핵심 분석을 계속 제공할 수 있다.

## 4. 핵심 기술 1: 근거 결속형 문서 AI

### 4.1 AI 출력 격리

문서 AI의 출력은 곧바로 금융 계산 입력이 되지 않는다. 추출 결과는 먼저 Pydantic
구조화 스키마를 통과하고, 국가명·날짜·금액·통화가 결정론적으로 정규화된다. 이후
당사자, 거래 방향, 통화, 금액, 결제일과 지급조건의 evidence가 실제 원문 페이지에
존재하는지 확인한다.

예를 들어 모델이 USD 100,000을 추출하더라도 인용한 문장이 다른 금액을 가리키거나
원문 페이지에 존재하지 않으면 해당 값은 계산에 전달되지 않는다. 사용자가 값을
수정하면 이전 evidence와 확인 fingerprint를 폐기하고 전체 검증을 다시 수행한다.

### 4.2 Human-in-the-loop 확인 gate

핵심 거래값은 사용자의 field-level 확인을 거쳐야 한다. 확인된 거래는 문서 SHA-256,
거래 방향, 통화, 금액, 결제일과 회차를 canonical JSON으로 직렬화한 뒤 fingerprint로
결속한다. Stage 2 입력의 fingerprint와 확인 기록이 다르면 오래되거나 변조된 상태로
판정하고 계산을 중단한다.

### 4.3 검증할 수 없으면 자동화하지 않는 fail-closed 정책

텍스트 레이어가 있는 PDF는 모델 인용을 독립적으로 대조할 수 있다. 반면 독립 OCR
원문이 없는 스캔·사진 문서는 같은 모델의 추출값과 인용만으로 진위를 증명하지 않는다.
이 경우 `OCR_REQUIRED`, `EVIDENCE_UNVERIFIABLE` 상태를 표시하고 사용자 확인 전
금융 계산을 차단한다. 이는 “모델이 답했으니 통과”가 아니라 **검증 가능한 근거가
있을 때만 자동화한다**는 금융 안전 설계다.

## 5. 핵심 기술 2: 시장모델의 의미와 적용 범위를 보존하는 시나리오 계층

Stage 1은 USD/KRW 방향 정보와 21거래일 경로위험 분위수를 제공한다. KBaiAgent는
이를 절대환율이나 실제 발생확률로 오해하지 않는다.

- 절대 기준환율은 별도의 `SpotRateProvider`에서 받는다.
- 수입은 환율 상승, 수출은 환율 하락을 불리한 방향으로 구분한다.
- `probability_calibrated=false`인 방향 점수는 시장 문맥으로만 사용한다.
- q90은 “90% 확률”이 아니라 모델 경로위험 분포의 분위수로 표시한다.
- 결제일이 21거래일 범위를 벗어나면 모델 분위수를 금액 계산에 외삽하지 않고
  `HORIZON_MISMATCH`를 남긴 뒤 ±3%, ±5%, ±10% 고정 스트레스로만 계산한다.
- HTTP provider가 실패하면 file/mock 또는 고정 스트레스로 전환하고 fallback 사실을
  사용자와 trace에 공개한다.

이 설계는 예측모델의 성능과 별개로, 모델 출력의 단위·시간 범위·통계적 의미가 후속
금융 계산에서 왜곡되지 않도록 한다.

## 6. 핵심 기술 3: Decimal 기반 금융 계산과 날짜별 현금 ledger

금융 숫자는 LLM이 아니라 Python `Decimal` 기반의 결정론 엔진이 계산한다. 날짜는
`date`·`datetime`으로 처리하고, 같은 입력은 항상 같은 결과를 만든다.

### 6.1 열린 환노출

```text
자연상계액 = 사용 가능한 보유 외화 + 결제일까지 확정된 동일통화 흐름
열린 환노출 = max(거래금액 - 자연상계액 - 기존 헤지금액, 0)
```

수입과 수출의 현금 의미도 분리한다. 수입은 외화 결제에 사용할 보유 외화와 동일통화
유입을 차감하고, 수출은 외화 수취액과 같은 통화의 확정 지출만 상계 후보로 본다.
기존 헤지는 노출에서 제외하되 약정환율과 수수료는 실제 원화 cashflow에 유지한다.

### 6.2 환율 시나리오별 영향

```text
수입 고객환율 = 기준환율 × (1 + spread_bps / 10,000)
수출 고객환율 = 기준환율 × (1 - spread_bps / 10,000)

수입 영향 = 시나리오 총지급액 - 기준 총지급액
수출 영향 = 기준 총수취액 - 시나리오 총수취액
```

유리한 시나리오는 음수 손실로 표시하지 않고 `loss_vs_base=0`으로 두며, 방향성은
`signed_impact_vs_base`에 별도로 보존한다.

### 6.3 세 가지 부족 개념의 분리

```text
buffer_shortfall = max(최소 운영자금 - 잔고, 0)
cash_deficit = max(-잔고, 0)
post_credit_deficit = max(-(잔고 + 신용한도), 0)
```

목표 운영자금보다 잔고가 적은 것, 현금잔고가 음수가 되는 것, 신용한도를 사용한
뒤에도 지급하지 못하는 것은 전혀 다른 위험이다. KBaiAgent는 세 값을 항상 분리하여
운영자금 목표 미달을 지급불능이나 필요 대출금으로 과장하지 않는다. 각 시나리오에는
날짜순 원화 유입·유출, 최저 잔고, 최초 부족일과 모든 숫자의 source path가 함께
저장된다.

## 7. 핵심 기술 4: 제약 기반 대응 후보 탐색

Stage 3은 상품 주문이나 자동 자문 엔진이 아니라, 공개된 가정 아래 대응 조합을
비교하는 결정론적 grid search다.

```text
선물환 비율 + 분할환전 비율 + 미헤지 비율 = 100%
```

후보는 다음 조건을 동시에 확인한다.

- 신규 선물환 최대 비율과 총 헤지 한도
- q90 불리 시나리오 손실한도
- 고정 ±10% 스트레스에서의 지급 가능성
- 최소 운영자금 유지 여부
- 신용한도 반영 후 실제 부족 0원
- 선택적 최소 거래 비율과 집중도 제한

조건을 만족하는 조합 중 안정성 우선, 균형, 비용 우선 관점의 후보를 최대 3개
제시한다. 실제 견적이 없으면 `SIMULATED_CANDIDATE`로 명시하며, 가능한 해가 없으면
후보를 억지로 생성하지 않고 `NO_FEASIBLE_CANDIDATE`와 실패 원인을 반환한다.

## 8. 핵심 기술 5: 공식 근거 RAG와 변조 방지형 상담 패킷

### 8.1 공식 출처만 사용하는 제한형 검색

공식자료 검색은 기본적으로 꺼져 있으며, 활성화 시에도 KB·한국무역보험공사·
중소벤처기업진흥공단 등 허용된 공식 도메인만 검색한다. URL은 검색 도구의 도메인
필터와 반환 결과 검증에서 이중 확인하고, 유사 도메인·비HTTPS 주소·출처나 확인일이
없는 결과는 제외한다. cache는 query·거래 방향·allowlist hash와 기본 24시간 TTL을
재검증한다.

사용자에게 노출하는 금융 후보는 검색 결과를 그대로 쓰지 않고 stable catalogue ID,
공식 출처, 활성 상태와 검증 상태가 고정된 버전형 catalogue에서만 투영한다. 거래
방향, 회사 역할, 상담 검토 분야, 필수·선택·제외·보류 신호를 결정론적으로 대조하고
동일 candidate family를 제거한 뒤 최대 3개만 남긴다. web 검색 결과는 자료 탐색에는
사용할 수 있지만 catalogue 검증을 거치지 않은 상태로 금융 shortlist에 바로
게시하지 않는다.

선적 상태, 수출채권 존재 여부, 거래 형태, 자금 용도, 조기 현금화·은행 조달 의사,
중소기업 여부와 같은 추가 조건은 `OfficialCandidateInputProfile`로 별도 확인한다.
각 값은 사용자·문서·기업정보 중 어디서 확인됐는지 provenance와 거래 fingerprint를
가져야 한다. `UNKNOWN`, `NO`, `NOT_APPLICABLE`을 서로 다르게 처리하며 필수정보가
없으면 후보를 추측하지 않고 보류한다. 상품 하위 유형도 자동 선택하지 않고 상담에서
확인한다.

사용자가 명시적으로 확인한 상품 전용 조건은 기존의 넓은 상담 신호보다 먼저
적용한다. 이 우선순위는 점수 엔진이 아니라 확인된 조건 충족 여부, 기존 상담 우선순위,
상품 분류와 stable ID의 고정 정렬이다. 상충하는 조건은 저장 전에 차단하거나 재확인을
요구한다. 적격 후보 중 Top 3 밖의 항목은 `overflow`, 정보가 부족한 항목은
`deferred`, 신용조사 같은 보조 서비스는 `auxiliary`로 분리하며 서로 바꾸어 표시하지
않는다.

가입 자격은 `UNKNOWN`, 승인 여부는 `CONSULTATION_REQUIRED`로 유지하며, 근거가
없으면 LLM이 상품을 만들어 채우지 않고 빈 상태를 반환한다. 금융 후보와 신용조사
같은 보조 서비스도 별도 목록으로 분리해 추천·승인처럼 보이지 않게 한다.

### 8.2 `ConsultationPacket`을 단일 진실 원천으로 사용

기존 위험 finding과 거래·회수 검토 항목은 공개된 category tie-break 규칙으로
정렬되어 상담 Top 3가 된다. 이 순서는 AI 추천점수나 금융 승인등급이 아니라 현재
거래에서 먼저 확인할 **검토 순서**다. 입력 collection 순서가 달라도 같은 rank와
fingerprint가 생성된다.

내부 priority는 사용자 화면에서 다시 두 층으로 투영된다. 금융 의사결정과 직접
연결되는 항목은 `수출대금 회수 보호`, `환율 관리`, `결제조건 보강`,
`무역금융·운영자금`, `정책자금 검토`의 핵심 검토 분야로 묶고, 거래정보 보완·국가
정보 완전성·거시환경 모니터링·시장접근 확인은 순위 배지 없는 추가 확인사항으로
분리한다. 모든 category가 두 층 중 정확히 하나에 매핑되지 않으면 fail closed한다.
따라서 정보 부족 경고가 금융지원 우선순위처럼 보이거나 기존 rank를 밀어내지 않는다.

각 상담 카드에는 다음 정보가 결속된다.

- 위험 발생 이유와 숫자 근거
- 숫자의 JSON source path
- 아직 확인되지 않은 정보
- 준비할 문서와 KB에 물을 질문
- 상담에서 기대하는 결정과 다음 행동
- 해당 범주에 연결된 공식자료 후보

화면, Markdown 다운로드와 Stage 5 보고서는 모두 동일한 `ConsultationPacket` JSON에서
파생된다. LLM은 이 JSON의 의미를 보조 설명하는 선택적 renderer일 뿐, 순위·숫자·
상품 범위를 바꿀 수 없다.

### 8.3 보고서 critic과 결정론 fallback

보고서의 숫자·날짜·통화·순위·상품명·기관명·URL은 먼저 결정론 코드가 작성한다.
LLM에는 실제 값이나 JSON path 대신 허용된 `source_id`와 각 source가 설명할 수 있는
의미 범위만 전달한다. LLM은 source ID마다 숫자가 없는 짧은 설명을 정확히 한 개씩
같은 순서로 반환해야 하며, renderer가 이를 canonical 보고서에 결합한다. 즉 생성
단계부터 LLM이 금융 숫자나 상품 식별자를 다시 쓸 기회를 제거한다.

결합된 보고서는 다시 deterministic critic을 통과한다. critic은 다음을 차단한다.

- 계산 JSON과 다른 숫자 또는 존재하지 않는 source path
- q90을 실제 확률로 표현하거나 스트레스를 예측으로 표현하는 문장
- 운영자금 버퍼 부족을 지급불능·필요 대출금으로 바꾸는 문장
- 예정 결제 노출을 실제 현재 미수·미지급잔액으로 표현하는 문장
- 계산상 후보를 최적 추천 또는 실행 지시로 표현하는 문장
- 상품 자격·승인·수익·손실 회피를 보장하는 문장
- 다운로드를 실제 RM 전송·예약·신청 완료로 표현하는 문장

검수 실패 시 최대 한 번만 수정하고, API 또는 재검수가 실패하면 동일 JSON을 직접
렌더링하는 결정론 보고서로 종료한다. 따라서 생성형 AI 장애가 핵심 계산이나 사용자
의사결정 근거의 소실로 이어지지 않는다.

## 9. 부가 맥락 데이터의 책임 경계

확정 거래의 상대국 무역통계와 국가환경 자료는 별도 맥락 카드로 제공한다. OECD,
World Bank, WTO와 관세청 공개 원자료는 원값·관측시점·출처를 보존하고, 자체 합산
신용등급이나 부도확률로 변환하지 않는다. 국가·무역 맥락은 보험·보증·신용장·
결제조건을 상담할 순서에만 사용하며, Stage 1 환율, Stage 2 현금흐름과 Stage 3 헤지
비율을 변경하지 않는다. HS Code도 상품명으로 추측하지 않고 사용자가 확인한 값만
사용한다.

환율 화면의 뉴스는 예측 모델이 계산한 숫자의 증명이나 입력이 아니라 분석 시점에
연결된 시장 배경이다. 저장된 기사 제목·출처·게시일·방향만 표시하고, 자료가 없거나
upstream이 unavailable이면 정상 empty state로 전환한다. 뉴스 부재는 환율 전망,
현금흐름 또는 공식 금융후보를 변경하지 않는다.

## 10. 대표 Golden 시나리오

2페이지 합성 수출계약을 기준으로 문서 업로드부터 상담 패킷까지 전체 흐름을
검증했다.

| 항목 | 결과 |
|---|---:|
| 분석 대상 예정 수취 노출 | USD 100,000 |
| 기준환율 | 1 USD = 1,400원 |
| 기준 원화 수취액 | 140,000,000원 |
| 환율 -5% 원화 수취액 | 133,000,000원 |
| 기준 대비 수취 감소 | 7,000,000원 |
| 스트레스 후 예상 현금 | 8,000,000원 |
| 최소 운영자금 기준 | 10,000,000원 |
| 운영자금 버퍼 부족 | 2,000,000원 |
| 현금 적자 | 0원 |
| 신용한도 반영 후 부족 | 0원 |

이 결과에서 시스템은 “200만 원 대출 필요” 또는 “지급불능”이라고 말하지 않는다.
현금은 양수이고 실제 부족도 0원이므로, 최신 자금계획과 수출대금 회수시점을 상담에서
확인하도록 안내한다.

상담 검토 순서는 다음과 같이 생성된다.

1. **수출대금 회수 보호**: Open Account/T/T 잔금 USD 80,000과 보호수단을 확인한다.
2. **환율 관리**: USD 100,000 예정 노출의 환율 하락 영향을 검토한다.
3. **운영자금 버퍼·회수시점**: 버퍼 부족 2,000,000원과 실제 deficit 0원을 함께
   확인한다.

계약상 USD 20,000 선지급 회차가 있어도 실제 입금 이력이 없으므로 현재 입금 상태는
`UNKNOWN`으로 유지한다. USD 100,000은 계약상 분석 대상 예정 노출이지 실제 현재
미수잔액이라고 주장하지 않는다.

## 11. 기술적 차별성

| 비교 대상 | 일반적 한계 | KBaiAgent의 방식 |
|---|---|---|
| 환율 계산기 | 거래 맥락·현금흐름·상담 행동이 없음 | 문서→환노출→현금 ledger→상담까지 연결 |
| 범용 LLM 챗봇 | 숫자 재계산, 환각, 근거 단절 가능 | AI 출력 격리, evidence·확인 gate, Decimal 계산 |
| 상품 추천 서비스 | 고객 적격성·승인을 과도하게 추정할 수 있음 | 공식 근거 후보만 표시하고 자격·승인은 사람에게 유지 |
| 단일 예측모델 | horizon 밖 외삽과 확률 오해 가능 | 모델·spot 분리, 21거래일 경계, 고정 stress fallback |
| 정적 보고서 | 화면·다운로드·설명 사이 숫자 불일치 가능 | 하나의 canonical packet과 fingerprint에서 모두 파생 |

핵심 차별점은 AI 모델 자체의 크기가 아니라 **AI와 금융 로직의 책임을 정확히
분리하면서도, 문서 원문부터 최종 상담 행동까지 provenance를 끊지 않는 것**이다.

## 12. 데이터셋과 검증 결과

### 12.1 재현 가능한 API-free 검증

- Python compile, 전체 unit·integration·E2E, fixture 흐름과 secret·schema 검사를
  `python scripts/verify.py` 한 명령으로 수행한다.
- 2026-08-03 제출 동결 작업트리에서 `python scripts/verify.py`를 다시 실행해 전체
  테스트 **707/707 PASS**와 release gate `VERIFY PASSED`를 확인했다.
- 수입·수출 대표 흐름, source-grounded evidence, 날짜·fingerprint 결속, 시장모델
  horizon, 세 부족 지표, 상담 Top 3, 공식 후보, critic과 fallback을 회귀 테스트로
  고정했다.
- Golden 계약 PDF는 SHA-256으로 고정하여 문서와 기대 결과의 임의 변경을 탐지한다.

### 12.2 문서 추출 평가의 주장 범위

- 기본 offline 평가 세트는 17건이며 저장된 fixture 기준 document pass 82.35%,
  hallucination 0%다. 이 수치는 evaluator·schema·validator의 결정론 회귀를 검증한
  결과이지 Live 모델 정확도 주장이 아니다.
- 미국·브라질 핵심 합성 8건은 수입·수출, 이미지형 PDF·JPG, 분할결제, 선지급,
  Net 60, 통화 누락과 가려진 결제일을 포함한다. 별도의 non-Golden 텍스트 PDF
  1건은 특정 Golden 문서에만 맞춘 recovery가 아닌지 경계를 검증한다. 이 자산들은
  모두 test split으로 고정하고 파인튜닝 후보에서 영구 제외한다.
- 독립 텍스트 원문이 없는 스캔형 Live 사례는 모델 응답 성공 여부와 무관하게 자동
  Stage 2 전달을 차단했다. 이는 OCR 정확도 0%가 아니라 검증 근거가 없을 때의
  fail-closed 동작을 뜻한다.
- source-grounded recovery 이후 승인된 제한된 합성 Golden 1건에서
  `validation_pass=true`, 사용자 확인 후 `stage2_allowed=true`를 확인했다. 이를
  전체 문서나 실제 고객환경의 정확도로 일반화하지 않는다.

### 12.3 평가 데이터 보호

모든 제출·평가 문서는 가상 당사자를 사용한 합성 데이터다. 실제 고객문서와
개인정보를 사용하지 않았으며, `split=test` 데이터는 파인튜닝 후보에서 항상
제외한다. Live 평가에서도 API key, 전체 prompt·payload, 문서 원문과 raw API
response를 저장하지 않는다.

## 13. 보안과 개인정보 보호

- PDF·PNG·JPEG만 허용하고 확장자, MIME, magic bytes를 교차 검증한다.
- 기본 15MB, PDF 20페이지 제한과 이미지 검증·strict PDF parse를 적용한다.
- archive, 암호화·손상·빈 PDF와 위장 파일을 차단한다.
- 업로드 bytes와 문서 원문은 메모리에서 처리하고 dataset·trace·로그에 자동 저장하지
  않는다.
- API key와 비밀값은 환경변수에서만 읽고, 오류에는 원문·응답·traceback을 노출하지
  않는다.
- 문서 안의 prompt injection 문구는 실행 지시가 아니라 비신뢰 데이터로 취급한다.
- Stage 1 REST는 URL·DNS·redirect를 검사해 사설·loopback·link-local·metadata
  endpoint 접근을 기본 차단한다.
- 공식 검색은 HTTPS와 도메인 allowlist를 이중 검증한다.

현재 보안 수준은 로컬 공모전 MVP의 안전 기본값이다. 운영 전환 전에는 사용자 인증,
tenant별 권한·데이터 격리, 악성파일 검사, sandbox PDF rendering, 동의·보존·삭제
정책, secret manager, 중앙 감사로그와 rate limit을 추가해야 한다.

## 15. 기대 효과와 KB 연계 가치

### 기업 고객

- 계약서 내용을 반복 입력하지 않고 확인된 핵심 거래값을 분석에 재사용한다.
- 막연한 환율 불안을 열린 노출, 추가 부담, 결제 후 현금과 부족 시점으로 이해한다.
- 상품명부터 찾는 대신 현재 거래에서 먼저 확인할 위험과 준비서류를 파악한다.

### KB 상담 담당자

- 거래 방향·통화·금액·결제일, 계산 가정, 위험 코드와 미확인 정보를 한 패킷에서
  검토한다.
- 고객과 동일한 숫자·source path를 보며 상담의 첫 질문을 구조화할 수 있다.
- AI 추천을 그대로 신뢰하는 대신, 공식 심사와 사람의 판단이 필요한 지점을 명확히
  확인한다.

### 향후 실증 KPI

현재 MVP에서 효과를 측정했다고 주장하지 않는다. KB 샌드박스와 사용자 실증 단계에서는
다음 지표로 가치를 검증할 계획이다.

- 계약서 접수부터 상담 준비자료 완성까지 걸린 시간
- 상담 전 필수정보 누락률과 재요청 횟수
- 원문 대비 핵심 필드 수정률
- 기업 담당자와 RM의 상담자료 이해도·만족도
- 상담 후 적합 부서·업무로 연결되는 비율
- 위험 숫자와 최종 handoff 간 불일치 건수

## 16. 현재 한계와 확장 로드맵

### 현재 한계

- 실제 고객문서 분포에서의 추출 성능과 사용자 효용을 아직 검증하지 않았다.
- 독립 OCR이 없는 스캔 문서는 안전하게 차단되지만 자동화율이 낮다.
- Stage 3 후보는 실제 은행 견적이 아닌 공개 가정 기반 비교안이다.
- 공식 후보는 최신 가격·한도·자격 판정이 아닌 출처 확인 자료다.
- 실제 KB 예약, RM 전송, 고객 매칭, 상품 신청·심사·헤지 주문은 구현하지 않았다.
- 인증·tenant·DB·운영 관측성을 갖춘 production 시스템은 후속 범위다.

### 확장 순서

1. 허가받은 비식별 문서로 독립 OCR과 field-level benchmark를 구축한다.
2. 기업 자금 담당자와 KB RM을 대상으로 과업 기반 usability test를 진행한다.
3. 인증·동의·tenant 격리·보존/삭제·감사로그를 포함한 운영 보안 계층을 추가한다.
4. KB 승인 API 계약을 통해 상담 예약·RM handoff를 연결한다.
5. 최신 상품·견적·적격성 데이터는 정책 버전과 설명 가능성을 확보한 뒤 별도 엔진으로
   연동한다.

## 17. 결론

KBaiAgent는 AI가 금융 결정을 대신하는 서비스가 아니다. AI는 다양한 무역문서를
읽고, 결정론 코드는 돈을 계산하며, 사용자는 거래 사실을 확인하고, 최종 금융 판단은
KB의 전문 상담과 심사가 담당한다.

이 책임 분리 덕분에 편리함과 안전성 중 하나를 포기하지 않는다. 문서의 한 문장에서
시작한 정보가 환노출, 현금흐름, 위험 코드, 공식자료와 상담 행동으로 이어지는 동안
근거와 의미를 보존한다. **KBaiAgent가 만드는 것은 또 하나의 환율 전망이 아니라,
기업과 KB가 더 빠르고 정확하게 같은 사실 위에서 대화를 시작할 수 있는 의사결정
인프라다.**

## 부록 A. 제출 양식용 요약문

KBaiAgent는 수출입 계약서·인보이스의 비정형 정보를 AI로 구조화하고, 원문 evidence와
사용자 확인을 통과한 값만 결정론적 금융 엔진에 전달하는 수출입 금융 의사결정 지원
에이전트다. 팀 Stage 1 시장모델과 독립 기준환율을 결합하되 21거래일 horizon 밖으로
예측값을 외삽하지 않으며, Python `Decimal`과 날짜별 ledger로 열린 환노출, 원화
지급·수취 변화, 운영자금 버퍼 부족, 현금 적자와 신용한도 반영 후 부족을 서로
구분해 계산한다. 이후 제약 기반 대응 후보와 공식 출처가 확인된 자료를 결합해 위험
기반 상담 Top 3, 숫자 근거, 부족정보, 준비서류와 은행 질문을 `ConsultationPacket`
JSON으로 생성한다. 화면·Markdown·최종 보고서는 이 단일 JSON에서 파생되며, LLM이
숫자·순위·상품 범위를 바꾸면 critic이 차단하고 결정론 보고서로 fallback한다. 실제
고객문서와 비밀값은 저장하지 않고 test split은 파인튜닝에서 제외한다. 핵심 원칙은
“AI는 읽고, 코드는 계산하고, 사람은 확인하고, KB는 결정한다”이다.

## 부록 B. 30초 기술 소개

> KBaiAgent의 핵심은 LLM에게 금융 계산을 시키지 않는 것입니다. AI는 계약서를
> 구조화하지만 원문 근거와 사용자 확인 전에는 어떤 값도 계산에 들어가지 않습니다.
> 확인된 거래만 Decimal 현금흐름 엔진으로 보내 환노출, 추가 손실, 운영자금 부족과
> 실제 지급 부족을 구분합니다. 그 결과는 공식자료와 함께 하나의 상담 패킷으로
> 묶이며, 화면과 다운로드 문서가 같은 숫자를 사용합니다. 즉 AI는 읽고, 코드는
> 계산하고, 사람은 확인하고, KB는 결정하는 구조입니다.
