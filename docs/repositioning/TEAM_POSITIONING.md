# 팀 회의 및 발표용 제품 포지셔닝

## 1. 기존 제품이 환율 계산기로 보일 수 있는 이유

기존 Stage 2 계산은 강했지만 화면의 핵심 흐름이 `환율 입력 → 원화 금액 → 부족 표시`로
읽혔습니다. 계산 뒤의 Stage 3은 가상 비용률을 사용하는 헤지 grid였고, Stage 4는
공식 상품 목록이어서 “기업의 어떤 위험 때문에 무엇을 상담해야 하는가”를 잇는
구조화된 근거가 없었습니다. 따라서 계산은 정확해도 제품 가치는 계산기처럼 보일 수
있었습니다.

## 2. 변경된 제품 포지셔닝

> 수출입 계약서 또는 거래정보를 구조화하고, 환율 변화가 기업의 실제 결제액과
> 운영자금에 미치는 영향을 결정론적으로 계산한 뒤, 검토할 외환·무역금융 대응과
> KB 상담 준비사항을 생성하는 수출입 금융 의사결정 지원 에이전트

짧게는 “수출입 거래의 환율 위험을 기업의 실제 현금 문제로 변환하고, 필요한 금융
상담까지 연결하는 AI 에이전트”라고 설명합니다.

이 화면의 주 사용자는 수출입 기업 재무·자금 담당자입니다. KB 담당자는 기업이
내려받아 공유한 JSON·Markdown 상담 패킷을 검토하는 후속 사용자입니다. 현재
저장소에는 다중 고객 관리, 상담 메모, 권한 같은 은행 직원용 case-management 기능이
없으므로 상담자 전용 제품이라고 설명하지 않습니다.

## 3. KB AI Challenge 주제와의 연결

이 MVP는 문서 AI 자체보다 `무역거래 → 기업별 금융 영향 → 상담 준비` 연결에
초점을 둡니다.

- 수출입 문서의 결제조건을 구조화합니다.
- 보유 외화·기존 헤지·현금·대출한도·예정 입출금을 기업별로 반영합니다.
- 수입은 환율 상승 비용, 수출은 환율 하락 수취 감소를 구분합니다.
- 위험 코드가 발생한 이유와 상담할 범주, 필요한 정보·서류·질문을 함께 제공합니다.
- 상품 가입이나 대출 승인은 확정하지 않고 KB 상담·심사로 넘깁니다.

## 4. AI가 필요한 이유

AI의 장점은 비정형 계약서와 인보이스에서 통화·금액·결제조건·거래 당사자와 원문
근거를 구조화하고, 복잡한 계산 JSON을 사람이 읽을 설명으로 바꾸는 데 있습니다.
서식과 문구가 제각각인 무역문서를 규칙만으로 모두 처리하는 것보다 AI 추출이
유용합니다.

다만 AI 출력은 사실이 아닐 수 있으므로 Pydantic schema, 원문 evidence, 결정론
검증과 사용자 확인을 통과해야 합니다. AI가 없어도 샘플 입력과 결정론 보고서로
데모가 끝까지 동작합니다.

## 5. 결정론적 계산이 필요한 이유

환율, 환노출, 원화 지급·수취액, 손실, 현금 잔고와 부족액은 동일 입력에서 언제나 같은
결과가 나와야 하고 감사 가능해야 합니다. 따라서 기존 `src/stage2/`가 `Decimal`과
날짜순 ledger로 계산하고, LLM은 숫자를 새로 만들지 않습니다.

특히 다음 두 지표를 분리합니다.

```text
buffer_shortfall
= max(최소 운영자금 - 결제 후 현금, 0)

payment_gap
= max(필요 자금 - 실제 현금·사용 가능한 대출자금, 0)
```

수입 대표 사례는 결제 후 현금이 940만 원으로 양수지만 최소 운영자금 1,000만 원보다
60만 원 부족합니다. 따라서 `LIQUIDITY_BUFFER_RISK`이고 지급불능
`PAYMENT_CAPACITY_RISK`가 아닙니다.

## 6. KB가 관심을 가질 수 있는 이유

기업은 막연히 “환율이 불안하다”가 아니라 열린 환노출, 결제 후 현금, 운영자금 부족과
확인할 질문을 들고 상담을 시작할 수 있습니다. KB 담당자는 거래 방향·금액·결제일,
시나리오, 계산 버전, 위험 코드, 미확인 정보와 준비서류를 한 패킷에서 확인할 수
있습니다. 이는 상품을 자동 판매하는 기능이 아니라 상담 전 정보 수집과 설명 시간을
줄이는 지원 도구입니다.

## 8. P0 완료 기능

- 거래 방향을 포함한 네 핵심 필드 사용자 확인
- 기존 Stage 2 금융 계산 재사용
- 수입·수출 방향별 구조화 위험 분류
- `buffer_shortfall`, 현금 적자, `payment_gap` 분리
- 위험 코드와 거래 방향을 사용하는 일반 상담 범주 매핑
- 사람 검토·은행 심사가 필요한 대응 후보
- 계산 숫자를 직접 복사하는 버전형 JSON·Markdown 상담 패킷
- 입력 hash, 환율 기준시각, 시나리오 ID, 원문 문서 hash와 확정 필드
- API 없는 수입·수출 대표 CLI 및 Streamlit 원클릭 흐름
- 184개 API-free 회귀 테스트

## 9. 미구현 기능

- KB 내부 상품·고객·심사 API
- 자동 상품 적격성, 대출 승인, 헤지 주문
- 실시간 환율 예측과 시나리오 확률
- 운영용 사용자 인증, 기업별 데이터 분리와 상담 이력
- 실제 문서 live benchmark, 운영용 악성파일 검사와 배포 인프라

발표에서는 위 항목을 현재 기능처럼 시연하지 않고 확장 계획으로만 설명합니다.

## 10. 3인 팀 역할 분담

공용 `schemas.py`, `src/domain/` 모델, Stage 1 JSON 계약, Stage 2 입력·결과 계약은
세 명의 합의 없이 변경하지 않습니다. 변경 시 schema, 샘플, 세 담당 영역의 테스트를
같은 PR에서 갱신합니다.

### 팀원 A · 거래 입력, 문서 추출, 사용자 흐름

- 담당 파일: `app.py`, `schemas.py`, `src/document_intake/`, `src/ui/`,
  `sample_data.py`
- 수정 가능 영역: 업로드·샘플 선택, AI 추출 adapter, evidence 표시, 네 필드 확인,
  기업 사용자 화면
- 수정하면 안 되는 인터페이스: `ConfirmationRecord`와
  `Stage2DocumentInput`의 확정 fingerprint 의미
- 완료조건: 샘플과 실제 모드에서 사용자 확인 전 Stage 2가 열리지 않고, 원문을
  저장·로그하지 않음
- 테스트: `python -m unittest tests.test_schemas_validators
  tests.test_upload_and_adapter tests.test_security_eval_demo -v`
- 연결 지점: 확정 거래 JSON과 hash를 팀원 C에게 전달

### 팀원 B · 환율 시나리오와 외부 adapter

- 담당 파일: `src/stage1/`, `src/config.py`, `samples/stage1_scenarios.json`,
  `docs/STAGE1_CONTRACT.md`
- 수정 가능 영역: JSON/REST adapter, 정규화, 수동 스트레스, timeout·fallback
- 수정하면 안 되는 인터페이스: Stage 1 팀의 외부 JSON 필드와
  `KRW_PER_1_FC` 내부 단위
- 완료조건: base 하나, 양수 환율, 통화·날짜·확률을 검증하고 외부 실패 시 표시된
  수동 fallback으로 전환
- 테스트: `python -m unittest tests.test_stage1 tests.test_upload_and_adapter -v`
- 연결 지점: `NormalizedScenarioSet`을 팀원 C의 계산과 패킷에 전달

### 팀원 C · 금융 계산, 위험, 상담 패킷, 통합

- 담당 파일: `src/stage2/`, `src/consultation/`, `src/application/`,
  `src/workflow/`, `tests/test_consultation.py`, `scripts/verify.py`
- 수정 가능 영역: 계산 버그, 위험 규칙, 상담 매핑, 패킷과 수입·수출 E2E
- 수정하면 안 되는 인터페이스: Stage 2 공개 DTO와 기존 계산 정의를 합의 없이 변경,
  LLM 숫자를 계산 입력으로 사용
- 완료조건: 대표 수입·수출 기대값, buffer/payment gap 분리, 상담 패킷 숫자 일치와
  사람 검토 필드가 테스트로 고정
- 테스트: `python -m unittest tests.test_stage2 tests.test_consultation
  tests.test_workflow -v` 및 `python scripts/verify.py`
- 연결 지점: 팀원 A의 확정 hash와 팀원 B의 시나리오를 받아 결과 계약을 UI에 제공

브랜치는 `feature/intake-ui`, `feature/stage1-adapter`,
`feature/risk-consultation`처럼 담당 경계별로 두고, 작은 커밋을 `main` 최신 기준으로
rebase한 뒤 PR로 통합합니다. 공용 계약 변경 PR은 세 명 모두 review합니다.

## 11. 30초 발표문

저희 서비스는 환율을 맞히는 서비스가 아닙니다. 수출입 거래정보와 기업 현금정보를
결합해 환율 변화가 실제 결제액과 운영자금에 미치는 영향을 계산합니다. 예를 들어
보유 달러를 제외한 열린 환노출과 결제 후 운영자금 부족을 구분해 보여줍니다. 이후
위험 원인과 검토할 금융 대응, 필요한 서류를 정리한 상담 패킷을 만들어 기업과 KB
담당자가 더 빠르게 상담할 수 있도록 돕습니다. 금융 숫자는 결정론 코드가 계산하고
AI는 문서 이해와 설명만 담당합니다.

## 13. 예상 질문과 답변

### 이게 그냥 계산기 아닌가?

환산만 하는 계산기와 달리 문서 확인, 보유 외화·헤지, 날짜별 기업 현금, 운영자금과
대출한도를 결합하고 위험 원인에서 상담 준비 패킷까지 연결합니다. 계산기는 핵심
안전장치이고 제품 가치는 기업별 의사결정 맥락과 다음 상담을 준비하는 데 있습니다.

### AI가 꼭 필요한가?

금융 계산에는 필요하지 않고 사용해서도 안 됩니다. 서식이 다양한 계약서·인보이스를
근거와 함께 구조화하고 계산 결과를 사용자가 이해할 설명으로 바꾸는 부분에서
필요합니다. API 실패 시 수동·샘플 입력과 결정론 보고서로 계속 동작합니다.

### 환율 예측이 틀리면 어떻게 하나?

이 MVP는 환율 방향을 맞힌다고 주장하지 않습니다. 사용자가 정한 기준과 불리한
스트레스 구간에서 현금이 버티는지 보는 민감도 분석입니다. Stage 1 전망을 연결해도
출처·기준시각과 `FORECAST` 상태를 표시합니다.

### 금융상품을 자동 추천해도 되는가?

하지 않습니다. 위험에 따라 상담 범주를 제시하고, 공식 근거가 있는 정보만 별도로
표시합니다. 적격성·한도·금리·가입과 실행은 KB 상담과 심사가 필요합니다.

### 외부 API나 LLM이 실패하면 어떻게 하나?

수입·수출 fixture, 수동 스트레스, 기존 결정론 계산, 일반 상담 규칙과 Markdown
템플릿이 있어 핵심 데모는 중단되지 않습니다. Stage 1 REST 실패도 표시된 수동
fallback으로 전환합니다.

### 기존 은행 서비스와 무엇이 다른가?

은행 상품 목록을 먼저 보여주는 대신 기업의 특정 수출입 거래와 현금 일정을 먼저
계산해 왜 상담이 필요한지 구조화합니다. 은행 서비스의 승인·실행 기능을 대체하지
않고 상담 전에 필요한 정보와 질문을 준비하는 앞단 도구입니다.
